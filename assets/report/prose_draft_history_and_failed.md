## 8.3.1 Iterative Design History

The software architecture of the Reactive Robot platform was built in seven phases, each responding to a limitation exposed by bench testing or live demonstration. Commit SHAs are cited inline so the progression can be followed directly in the project's version control history.

The initial sensing pipeline was established on 2026-03-04 [commit 653d689]. A `tof_sensor.py` module was introduced to consume the Teensy 4.1 serial stream, parse the 8x8 VL53L5CX distance grids, and expose them to the host application alongside a Lark-based configuration layer and the ToFPlotter visualisation utility. At this stage no motion logic was coupled to the sensor data; the pipeline served only to validate that per-channel ranging was stable across the TCA9548A multiplexer.

The second phase, executed on 2026-04-10 [commits ec57cdd through 574fec6], delivered a digital twin in a single day. Seven sub-tasks were completed: a PyBullet simulator built against a backend Protocol abstraction, a Lark domain-specific language for motion primitives, a FastAPI and WebSocket bridge, a Three.js viewer, a Blockly-based visual editor, live canvas recording, and a hardware/simulator mode toggle. The twin provided a safe iteration surface for subsequent avoidance work, eliminating the need to risk the physical arm for every algorithmic change.

First-generation obstacle avoidance was introduced on 2026-03-25 [commit bc383b4]. A Kalman-filtered centroid tracker was implemented in `obstacle_map.py` using a six-state constant-velocity model, a sweep state machine with IDLE, RUNNING, PAUSED_OBSTACLE, and BACK_AWAY states was implemented in `auto_sweep.py`, and thread-safe IMU fusion was added in `imu_state.py`. ToF frames were projected to the world frame through the forward-kinematic chain and the IMU rotation matrix, and forbidden-theta bands were derived so that the sweep could jump past detected obstacles.

Persistent obstacle memory was added on 2026-04-09 [commit 78bd58f]. The `obstacle_memory.py` module introduced a sparse voxel grid with confidence-based decay, allowing detections to be retained across the gaps inherent to the ToF field of view.

On 2026-04-10 [commit a29998d] the MotionGuard chokepoint was introduced after a field failure in which the top/side ToF channel had been treated as advisory only; this incident is documented in Section 13. The commit promoted the channel to replan authority, routed every manual and autonomous target through `motion_guard.py`, corrected a retreat direction that had been smaller than the sensor field of view, added a 10 Hz JSONL session logger, and introduced hysteresis on infrared and obstacle state transitions.

A research-backed consolidation followed on 2026-04-15 [commit abf1530], replacing the ad-hoc MotionGuard, auto-sweep, obstacle-map and obstacle-memory modules with a twelve-module `braccio_ctrl/safety/` package described in Section 8.3.2.

Work currently in progress, begun on 2026-04-19 [commits 798c861 through 6d25677], extends the platform with a reinforcement-learning data pipeline comprising a 74-float observation encoder, a transition recorder, an eight-term reward function, DTW-based path annotation, a Gym environment, and a four-dimensional action space. The safety stack retains blocking authority over all learned policies.

## 8.3.2 Safety Stack Architecture

The current safety architecture enforces one rule: every commanded motion is routed through a single chokepoint before any byte is written to the arm controller. This applies to keyboard teleoperation, autonomous sweep, scripted sequences, and learned policies alike. That chokepoint is the `SafetyAPI` class in `api.py` (515 lines of code), which exposes `plan_and_validate()`, `queue_manual_intent()`, and `queue_sequence()` as the only sanctioned entry points into motion. Bypass paths have been removed from the codebase; if a module wishes to move the arm, it must present its target to the API and accept the verdict returned.

Internally the API is backed by a py_trees behaviour tree implemented in `behavior.py` (835 LOC). Selector nodes arbitrate between competing tasks — manual intents, sweep continuation, recovery manoeuvres, and idle holds — and sequence nodes enforce the ordering of pre-scan, plan, validate, and dispatch steps for each accepted motion. The tree tick rate is synchronised with the 10 Hz sweep cadence, ensuring that every behavioural decision is re-evaluated against fresh sensor state.

World state is maintained in `world_model.py` (348 LOC) through a dual representation. A KDTree is built over the live point cloud to answer nearest-neighbour distance queries in logarithmic time, and a log-odds occupancy grid accumulates confidence over repeated observations. This pairing supersedes the earlier Kalman tracker and voxel memory with a single representation that serves both instantaneous collision queries and longer-horizon persistence.

Collision checking is performed in `collision.py` (267 LOC) against capsules derived from the full arm kinematic chain. The capsule list itself is produced by `fk.py` (342 LOC), which drives forward kinematics through a PyBullet URDF model of the Braccio V2. Every proposed configuration is tested by computing the minimum distance between each link capsule and every point in the KDTree, so that avoidance is enforced along the entire arm and not only at the end effector.

Path planning is delegated to `planner.py` (350 LOC), a thin wrapper over the pybullet-planning BiRRT implementation operating in joint space. When a direct plan fails, `replanner.py` (251 LOC) invokes a six-strategy recovery ladder that progresses from essential-waypoint reduction, through via-point insertion, to controlled retreat. Before any plan is committed, `pre_scan.py` (113 LOC) articulates the wrist through two or three orientations so that blind spots caused by the fixed mounting geometry of the ToF quartet are eliminated.

Two additional supports complete the stack. A one-dimensional polar occupancy grid in `polar_map.py` (243 LOC) records forbidden theta bands so that the sweep can skip past known obstacles without re-triggering the full replan pipeline on every tick. Reusable signal-conditioning primitives — debounce, latch, and rate-limit — are provided by `hysteresis.py` (130 LOC) and applied to infrared severity, obstacle-transition flags, and manual-input streams. Refusal messages for rejected manual intents are routed through `dialog.py` (175 LOC), and the package surface is curated by `__init__.py` (89 LOC).

The guarantee that follows is that no motion command is issued unless the entire arm body is collision-free along every waypoint of the planned path, checked against both the live point cloud and the accumulated occupancy grid.

## 13.x Initial Obstacle Avoidance Approach

The first working obstacle-avoidance implementation on the platform was introduced on 2026-03-25 [commit bc383b4] and was based on centroid tracking combined with forbidden-theta bands. Each ToF frame was converted from its local sensor frame into the world frame by applying the forward-kinematic transform of the mounting joint and the cached IMU rotation matrix. The resulting point cloud was reduced to a single centroid per detected cluster, and a six-state constant-velocity Kalman filter was maintained for each active track in `obstacle_map.py`. A helper method, `get_obstacle_thetas()`, translated the tracked centroids into forbidden bands in base-angle space, and the sweep state machine in `auto_sweep.py` consulted these bands at each tick so that the arm could "jump past" an obstacle with a fixed angular margin.

Three field failures invalidated this approach. The first occurred during a live demonstration on 2026-04-10: channel 2, which was mounted to face upward and was classified as advisory with a 50 mm threshold, fired as a user's hand passed at approximately 100 mm, but because the motion-command gate ignored advisory channels, the arm continued its sweep and struck the hand. The second failure was geometric. The scripted retreat on obstacle detection executed a 30 degree reverse, but the ToF field of view subtended 45 degrees, so reversing by less than the sensor aperture actually translated the arm body toward portions of the obstacle that had not been in view when the retreat began, reducing rather than increasing clearance. The third failure was architectural: manual keyboard commands were exempt from live sensor gating entirely, being checked only against the voxel memory, which was subject to a populate delay of approximately 500 ms. A freshly detected obstacle therefore did not protect the arm from an immediate teleoperated command that would collide with it.

These three failures together motivated the 2026-04-15 safety-stack refactor [commit abf1530], in which the synchronous `SafetyAPI` chokepoint was introduced, all ToF channels were promoted to replan authority at a uniform 250 mm threshold, and per-command capsule checks against the live point cloud were made mandatory regardless of command origin.
