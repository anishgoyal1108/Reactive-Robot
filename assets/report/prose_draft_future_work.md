## Future Work

The system described in the preceding sections meets the project's primary objective of reactive obstacle avoidance on a 6-DOF Braccio V2 arm. Six directions remain open for extension, ordered below from the most immediate hardware and perception upgrades to a longer-horizon protocol-level proposal for decentralized cooperation between multiple arms.

### Camera Vision with Object Detection

The current perception stack relies exclusively on geometric sensing. Time-of-flight and infrared channels report the *presence* of an obstacle and its approximate distance, but no semantic information is available: a human hand and a ceramic mug are treated identically once they enter the capsule-collision envelope. For a collaborative robotic system this gap matters, because the minimum clearance that should be enforced around a human hand differs from that around an inanimate object by roughly an order of magnitude.

A monocular RGB camera, such as a Raspberry Pi Camera Module v3, is proposed as an additional perception channel. A lightweight object detector from the YOLO family [1] is run on a companion Jetson Nano, with detections projected into the arm's world frame using the known camera extrinsics and fused with the existing point cloud maintained by `world_model`. The safety API is then extended to accept class-conditioned clearance parameters, so that a larger exclusion radius is enforced around a detected hand than around an inanimate object. The integration point in the current codebase is a new observation channel feeding `braccio_ctrl/safety/world_model.py` alongside the existing ToF clouds; no change to the behavior tree or the capsule-collision routines is required, because those operate on the fused world model rather than on raw sensor frames.

### Sensor Bandwidth Optimization

A practical bottleneck in the present deployment is the shared serial link between the Teensy 4.1 and the host computer. The four VL53L5CX sensors are each capable of an 8×8 ranging frame at approximately 15 Hz, but because all four share a single USB-serial channel at the current baud rate and frame format, the effective per-sensor update rate is roughly one quarter of that native maximum. The reactive safety loop is consequently starved of fresh distance data in the interval between frames, which is visible as latency between obstacle appearance and detection.

Three complementary mitigations are proposed. First, the Teensy 4.1 USB-serial interface is capable of baud rates well above the current configuration, with 1 Mbaud and higher being readily achievable; raising the baud rate is the lowest-effort improvement. Second, the existing CSV-like framing (`TF,<seq>,<ms>,S<ch>,...`) is replaced with a compact binary frame schema in which sensor identifiers, timestamps, and distance arrays are packed as fixed-width integers, eliminating the per-character parsing overhead on both ends. Third, because the Teensy 4.1 exposes multiple hardware UARTs, a second physical serial interface is added so that ToF traffic and IR/IMU traffic are carried on independent links. The combined target is restoration of the per-sensor update rate toward the sensor's native 15 Hz, which directly tightens the reactive safety loop.

### IMU Yaw Integration

The current IMU fusion pipeline uses only the MPU-6050 accelerometer for roll and pitch, and the arm's yaw is inferred geometrically from the commanded base servo angle. This is adequate while the arm's base is rigidly fixed to the workbench and the servo is assumed to be free of backlash, but it fails as soon as the whole platform is repositioned or the base servo accumulates error.

Integrating gyroscope-derived yaw with a magnetometer reference removes this dependency on servo state. A three-axis magnetometer such as the HMC5883L is added to the existing I2C bus alongside the MPU-6050, and a complementary or Mahony filter fuses the gyroscope rate with the magnetometer heading to produce a drift-corrected yaw estimate. With an authoritative heading available, the world-frame projection of obstacle observations remains correct when the arm base rotates relative to the workbench, when the platform is lifted and replaced, or when the servo's zero reference drifts over the course of a session. The obstacle memory, which presently must be cleared on IMU recalibration, is then able to persist across such events.

### Additional IR Sensors

The current four IR proximity sensors are positioned to cover the primary sweep zone at the forearm and wrist, which has proven sufficient for single-axis obstacle avoidance. However, the coverage is inherently sparse: a thin obstacle passing between two sensors in the current layout is not detected by the IR channel and is only caught by the ToF fan-out. Denser placement of eight or more IR sensors distributed along the forearm, wrist, and gripper approaches the "electronic skin" concept used in collaborative industrial arms [2], where a near-continuous shell of short-range presence detectors allows the controller to respond to contact from any direction.

The per-sensor cost of the active-low IR modules used in the present system is below five dollars, and the Teensy 4.1 provides ample digital input pins for the proposed expansion. The practical limits are therefore mounting geometry and cable management rather than electronics. A 3D-printed sensor shell matched to the Braccio V2's forearm and wrist profile is proposed, with IR modules embedded flush at fixed angular spacing.

### Reinforcement Learning

A reinforcement learning pipeline has been developed in parallel with the classical safety stack but has not yet produced a trained policy ready for deployment. The pipeline comprises a 74-float observation encoder (joint state, ToF summary statistics, IR severity, obstacle-memory features, and progress indicators), a 4-dimensional continuous action space (Δθ, Δr, Δz, Δreach), a Gym-compatible environment, and a reward function derived from dynamic-time-warping similarity between executed trajectories and human demonstrations.

The intended role of the learned policy is as a drop-in replacement for the existing sweep controller, not for the safety stack itself. The policy emits incremental targets in (θ, r, z, reach) at the same 10 Hz cadence as the current sweep daemon, and every commanded increment is routed through `SafetyAPI.plan_and_validate` exactly as a manual or scripted command is. The safety stack therefore retains veto authority over every motion regardless of the policy's output, which preserves the reactive guarantees established in the classical design. Training is conducted in the existing PyBullet digital twin with domain randomization across ToF noise models, servo command latency, and obstacle distribution statistics, so that the policy is not over-fitted to the idealized simulator dynamics.

### Protocol Layer for Decentralized Agentic Cooperation

The final proposed direction is the most speculative, and motivates a longer discussion. *Decentralized cooperation* is defined here as a multi-agent regime in which no single agent holds the full world model, no agent issues commands to other agents, and the shared objective is not imposed top-down by a coordinator. Each agent acts to maximize its own reward signal on the basis of its own local observations; cooperative behavior, where it emerges, does so because the individual reward signals are correctly aligned with the shared task. This framing follows the *reward-is-enough* hypothesis advanced by Silver, Singh, Precup, and Sutton [3], which argues that intelligence and its associated abilities—perception, planning, and, critically for the present proposal, cooperation—can be understood as emerging from the maximization of an appropriately specified reward. The contrast with centralized planning is sharp: in a centralized regime a single process owns the world state and issues coordinated commands, whereas in a decentralized regime the world state is distributed across peers and coordination is an emergent consequence of aligned rewards.

The motivation for extending the current single-arm system in this direction is straightforward. A single Reactive Robot arm already benefits internally from sensor fusion across its own ToF and IR channels; multiple arms cooperating in a shared workspace—for instance, a two-arm bimanual manipulation cell or a small fleet of arms on an assembly line—would benefit analogously from sharing obstacle observations, announcements of near-term intent, and soft reservations over workspace regions. A centralized coordinator scales poorly as the number of arms grows and introduces a single point of failure; a thin peer-to-peer protocol layer does not.

The protocol is proposed at an engineering-report level of detail, sufficient for a follow-on team to implement. *Discovery* is handled by UDP multicast on the local subnet, with each robot announcing its identity and capability set at 1 Hz. *State announcement* is performed at 10 Hz: each robot broadcasts a compact message containing its robot identifier, a timestamp, the current end-effector pose expressed in a shared world frame, the next planned target pose, a summary of per-sensor obstacle observations, an estimate of the local reward vector, and a scalar confidence value. *Intent negotiation* is triggered when two robots' planned paths are predicted to intersect within a configurable spatial and temporal margin; both robots then broadcast an intent-bid carrying their current reward-to-go, the robot with the higher bid proceeds, and the robot with the lower bid defers and replans. Ties are broken deterministically by comparison of robot identifier. The *shared world model* is not a single centralized structure but is maintained locally by each robot, with peer observations fused into the local model under a confidence discount so that own-sensor observations are always weighted above peer-sensor observations. *Failure modes* are handled by the stateless nature of the broadcast design: message loss requires no session recovery, reward-bid ties are resolved deterministically without additional messaging, and the absence of peer presence announcements is interpreted as peer unavailability rather than as evidence of a clear workspace.

A clarification is in order. The protocol does not cause cooperation; the reward structure does. The protocol layer is only the plumbing that lets each agent's reward signal see and react to the other agents' states. Cooperative behavior emerges when the reward structures are correctly specified, consistent with the *Reward is Enough* argument. A well-engineered protocol cannot compensate for misaligned rewards, and a poorly engineered protocol cannot prevent well-aligned rewards from producing cooperative equilibria. The engineering contribution of this subsystem is therefore the protocol itself; the research contribution is the specification of reward functions that, acting through the protocol, produce the target cooperative behavior on shared manipulation tasks.
